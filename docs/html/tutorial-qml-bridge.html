    Tutorial 6: Connecting the Core to QML

    The core runs in its own thread and knows no Qt. QML runs in the GUI thread. A thin bridge connects them.

    Events out

    The core reports changes through a plain C++ interface:

    class igame_observer_t
{
public:
    virtual ~igame_observer_t() = default;

    virtual void on_game_tick() = 0;
    virtual void on_creature_created(const creature_t& creature_p) = 0;

    Changing threads

    GameObserver implements it and moves each event to the GUI thread:

    void GameObserver::on_creature_health_changed(
    std::uint64_t id_p,
    int health_p
)
{
    QMetaObject::invokeMethod(
        this,
        [this, id_p, health_p]() {
            emit creatureHealthChanged(id_p, health_p);
        },
        Qt::QueuedConnection
    );
}

    Qt::QueuedConnection runs the lambda in the GUI thread, so QML never sees half updated data.

    Models and commands

    GameBackend owns one list model per kind of object (creatures, bases, base actions, corpses) and forwards input to the core:

        Q_INVOKABLE void orderBaseAction(const QString& key_p);

    Example use in QML:

    Repeater {
    model: gameBackend.creaturesModel
    delegate: CreatureView {}
}

onClicked: gameBackend.orderBaseAction("spawn:orc")

    The core checks every command. QML cannot, for example, move the units of another race.

    Adding new data to the screen

    Always the same path:

    1. Add a function to igame_observer_t and call it in the core.
    2. Emit a signal from GameObserver.
    3. Update a model or a property in GameBackend.
    4. Bind to it in QML.
