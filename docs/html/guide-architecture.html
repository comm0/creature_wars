    Architecture

    Creature Wars is built like an MMORPG server monolith. One core owns the game world and the client only shows it. Right now both live in one process, but they only talk through a narrow interface, so the core could move into a server without big changes.

    Game corebackend/*.h, backend/*.cpp with _t typesPlain C++20 and nlohmann/json. No Qt.

    Clientqml/Felgo, QML and the properties and models of GameBackend.

    Threads

    There are two threads. The GUI thread runs QML, Felgo and the bridge. The game thread belongs to game_t and is the only thread that ever reads or writes the game state. The two meet in exactly two places:

    • Commands. request_* functions of game_t take a small lambda, push it into a mutex protected queue and wake the game thread.
    • Events. The game thread calls igame_observer_t. GameObserver copies the data and posts it to the GUI thread with Qt::QueuedConnection.

    Nothing else is shared, so the game logic needs no locking at all.

    Inside the game thread

    1. Sleep until the next scheduled event or creature step, or until a command arrives.
    2. Move queued commands into game_event_dispatcher_t.
    3. Move every event from game_scheduler_t whose time has come into the dispatcher.
    4. Run the dispatcher, which executes everything in arrival order.
    5. Advance creature movement that is due.

    The game tick is itself a scheduled event that runs once per second of game time and reschedules itself. It lets creatures think, attack, regenerate and removes the dead. Income, base orders, AI decisions and wildlife spawns are scheduled events too.

    game_clock_t sits between the wall clock and the scheduler. Pausing stops game time and changing the speed scales it, and scheduled events simply follow.

    Controllers

    Each race in a match has a controller with its resources, research, order queues and a flag that says whether a human plays it. Player input and AI decisions end up in the same functions, so both follow the same rules. ai_planner_t decides for the computer controlled races, with numbers from data/ai_profiles.json.

    Data

    FileContent
    data/creature_types.jsonCreature stats, colours, behaviour, area damage
    data/base_types.jsonBase stats per level, units with training costs, rewards
    data/tech_tree.jsonBase upgrade costs and research paths
    data/economy.jsonStarting resources, income and the income bonus per level
    data/ai_profiles.jsonEasy, normal and hard AI settings

    All files are loaded once when GameBackend creates the game. Invalid values throw an exception with a message, so mistakes show up right at start.

    Toward online play

    To split the game into a server and clients, the plan is to keep game_t as it is and replace the two meeting points. The observer would serialize events into messages and send them to connected clients. The request_* calls would come from network messages. The QML client would keep its models and simply fill them from the network instead of from a local GameObserver.
